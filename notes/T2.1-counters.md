# T2.1. Сравнение счётчиков

Стенд: `lab.concurrency.counter.CounterBenchmark`, 8 потоков по 1 000 000 инкрементов, ожидается 8 000 000.

Окружение: AMD Ryzen 5 3550H (4 ядра, 8 потоков), OpenJDK 25.0.4.1.

```bash
./gradlew classes && java -cp build/classes/java/main lab.concurrency.counter.CounterBenchmark
```

Стенд запускался в трёх отдельных JVM. В каждой JVM: 3 раунда разогрева (результаты отброшены), 5 прогонов для замера времени и ещё 10 для проверки значений.

## Почему volatile не спасает

`volatile` гарантирует видимость и порядок: чтение поля видит последнюю запись в него. Атомарности составной операции он не даёт. `count++` в `VolatileCounter` компилируется в отдельные чтение и запись (вывод `javap -c`):

```text
getfield  count   // чтение
lconst_1
ladd              // +1
putfield  count   // запись
```

Между `getfield` и `putfield` другой поток может успеть записать своё значение, и оно будет затёрто:

| Шаг | Поток A | Поток B | `count` |
| ---: | --- | --- | ---: |
| 1 | читает 5 | | 5 |
| 2 | | читает 5 | 5 |
| 3 | пишет 6 | | 6 |
| 4 | | пишет 6 | 6 |

Два инкремента увеличили счётчик на 1. Оба потока работали с актуальными данными, то есть с видимостью здесь всё в порядке: проблема в том, что шаги чтения и записи можно разделить.

Поэтому `VolatileCounter` теряет инкременты так же, как `UnsafeCounter`, и при этом работает медленнее: каждая запись в `volatile` требует барьера памяти. Исправить это может только атомарная операция (`AtomicLong`, `LongAdder`) или взаимное исключение (`synchronized`).

## Почему LongAdder быстрее AtomicLong при высокой конкуренции

На стенде `AdderCounter` быстрее `AtomicCounter` в 5,6–15,6 раза, в зависимости от того, в какую группу попала медиана `AtomicCounter`.

**`AtomicLong`: одна ячейка на всех.** Все потоки обновляют одно и то же поле. Перед записью ядро должно получить кэш-линию с этим полем в монопольное владение, поэтому линия постоянно переходит между ядрами, и обновления выполняются строго по очереди. На x86 `incrementAndGet` обычно сводится к `lock xadd`, без повторных попыток CAS, но очередь за кэш-линией всё равно остаётся. Добавление потоков не ускоряет работу: все они упираются в одну линию.

**`LongAdder`: своя ячейка у каждого потока, по возможности.** Сначала он пробует CAS по общему полю `base`. При первом конфликте создаётся массив ячеек `Cell`, и потоки по своему хешу (probe) пишут каждый в свою ячейку. При повторных конфликтах массив растёт, но не больше числа ядер, а поток получает новый хеш. Ячейки помечены `@Contended`, поэтому лежат в разных кэш-линиях и не мешают друг другу из-за ложного разделения. В итоге большая часть инкрементов проходит без конкуренции, и потоки работают почти параллельно.

**Цена `LongAdder`.** Значение нигде не хранится целиком, и `sum()` складывает `base` и все ячейки:

- чтение дороже и занимает больше памяти;
- во время параллельных записей `sum()` не даёт точного снимка. На стенде значение точное, потому что оно читается после завершения всех потоков;
- нет атомарных операций вроде `compareAndSet` и `incrementAndGet`.

**Вывод.** `LongAdder` подходит, когда пишут часто, а читают редко (метрики, статистика). `AtomicLong` нужен, когда при каждом обновлении важно точное значение: генерация идентификаторов, CAS-логика.
